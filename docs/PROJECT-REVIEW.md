# Project review — 18 September 2026

This is a source review and targeted hardening pass, not a penetration test, accessibility certification, or legal opinion. Canada/Alberta is a provisional operating assumption; the business location and client markets have not been confirmed. No production accounts, data, provider settings, or deployments were changed.

## Changes implemented

| Priority | Finding | Change |
| --- | --- | --- |
| High | `auth.ts` granted operator privileges to any signed-in account whose email matched `ADMIN_EMAILS`, even before verification. Registration immediately creates a session. An attacker could register an as-yet-unused allowlisted address. | Admin policy now requires a verified, non-demo account for both environment and database grants. Existing unverified operators must complete `/verify`. |
| Medium | The browser mutation guard compared hosts, allowing a different protocol, and malformed origins could throw unexpected errors. | Compare complete HTTP(S) origins, reject malformed/opaque origins with 403, disregard the separate Host header, and reject explicitly cross-site browser requests without Origin. Originless API clients remain supported. |
| Medium | Guest and admin multipart uploads could allocate the whole body before enforcing size; a missing or false Content-Length bypassed the early check. | Count streamed bytes before parsing multipart data. Apply this to guest photos, finder maps, social media and design photos. Hosting limits may be lower than application limits. |
| Maintainability | Account and design endpoints duplicated bounded request parsing; parsing imported the database/session module solely for its error type. | Share byte, JSON and form readers. Extract HTTP errors, origin policy and admin policy into `src/lib/security/`; preserve existing auth exports. Story password JSON is now bounded too. |
| Client clarity | Privacy choices did not explain the difference between the public story and a household bearer link. | Show contextual explanations beside publishing settings, including how to revoke a forwarded invitation. |
| Accessibility | The film slider omitted its current accessible value and did not support Home/End. Seeking to the exact duration loops to the beginning. | Keep the accessible value synchronized, add arrow/Home/End controls, prevent keyboard page scrolling and hold the final frame when seeking to the end. |

Security regression tests exercise unverified admin claims, demo exclusion, protocol/port mismatch, malformed and cross-site origins, false upload lengths and valid multipart preservation.

## Strong foundations to retain

The project already has salted password hashes, hashed invitation/session tokens, secure production cookies, parameterized database queries, wedding-level authorization, consent-filtered messaging, photo re-encoding, private guest photo storage, webhook signature checks and browser workflow tests. The studio panels already have useful workflow boundaries. These are reasons to refactor incrementally rather than replace the application.

## Remaining engineering priorities

1. **Operator account protection — mostly done 18 Sept:** optional TOTP two-factor authentication is implemented (`src/lib/totp.ts`, `src/lib/mfa.ts`; correctness verified against the RFC 6238 test vectors and end-to-end against a live server, including one-time backup codes and login-challenge attempt limits). Account deletion and data export now require a fresh password (plus a current MFA code when enabled) — see the `reauth` and `deletion-request` actions in `src/app/api/auth/[action]/route.ts`. Passkeys are not implemented. Collaborator role grants remain gated only by existing owner/partner checks, not step-up reauth. Assessing whether existing allowlisted accounts were legitimately verified is still an operator task; this review does not establish prior exploitation.
2. **Request and abuse boundaries — trusted-proxy IP handling done 18 Sept:** every rate limit now reads `clientIp()` (`src/lib/security/client-ip.ts`) instead of the raw `x-forwarded-for` header. It trusts the header on Vercel (whose edge overwrites client-supplied values) or when the operator explicitly sets `TRUST_PROXY=true` for their own reverse proxy; otherwise every rate-limited action shares one bucket instead of trusting a spoofable per-request claim. Verified with unit tests and a live server. Signed webhooks — done 18 Sept: both `src/app/api/webhooks/resend/route.ts` and `stripe/route.ts` now read the raw body through the existing `readBytes()` (2 MB cap, enforced during the stream, not just via a spoofable Content-Length) before verifying the signature over those exact bytes, and return a clean 4xx on overflow instead of an unhandled 500 — verified live that a valid signature still passes and an oversized body is rejected in milliseconds. Synchronous scrypt — done 18 Sept: `passwordHash`/`passwordMatches` in `src/lib/auth.ts` now use `node:crypto`'s async `scrypt` (via `promisify`), so the derivation runs on libuv's threadpool instead of blocking the main event loop during a login storm. This is an async-signature change touching every call site — 13 across `src/app/api/auth/[action]/route.ts`, `src/app/api/[...path]/route.ts`, `src/app/api/story/unlock/route.ts`, and `src/lib/seed.ts` — all updated and each individually re-verified live (register, correct/wrong login twice over, reauth, and the wedding story password) to confirm wrong credentials are still rejected and correct ones still succeed; a missed `await` here would have silently made every password check pass. Load testing under real concurrency has not been done.
3. **Retention and deletion — partially done 18 Sept:** an idempotent, retrying file-deletion queue (`pending_file_deletions`) now runs for both demo cleanup and self-service account deletion (`src/lib/account-deletion.ts`, migration 021). Still open: design originals, public finder media, and enquiry records are not yet routed through this queue, and backup expiry is unaddressed. The README now documents self-service deletion but the operator-run manual procedure remains for out-of-band requests.
4. **Browser hardening — CSP done 18 Sept, with a real tradeoff surfaced and resolved:** a first attempt at nonce-based `script-src` (dropping `'unsafe-inline'`) forced every page in the app out of static generation, including the marketing homepage — a nonce is inherently per-request, which is fundamentally incompatible with pre-rendering the same HTML for everyone. Caught this via a live build/render check before shipping it, not after. The actual policy (`src/middleware.ts`) instead applies the strict nonce policy only to routes that already render per-request account/guest/wedding data and were already dynamic before this change (admin, contact, design-preview, documents, day-of finder, guest invitations, login/start/verify, Studio, the public story page — see `STRICT_PREFIXES`); each of those routes reads the nonce via `src/lib/csp-nonce.ts` in its own `page.tsx`, which is what makes Next.js stamp its own bootstrap scripts with it. The marketing/legal pages keep the permissive fallback and their static generation. Verified with a rebuild confirming the exact same static/dynamic route split as before, and a live Playwright pass across marketing, login, guest-invitation-opening, and Studio with zero CSP violations and zero console errors. `src/middleware.ts` → `src/proxy.ts` (Next.js's replacement convention, `export function proxy` instead of `middleware`) was applied once the tree was clean, via the official `@next/codemod middleware-to-proxy`, and re-verified with a full rebuild (no deprecation warning) and the same live Playwright pass. Accessibility keyboard/contrast testing is now covered by `scripts/audit-accessibility.mjs` and `scripts/audit-keyboard.mjs` (see the roadmap table above) — full manual assistive-tech testing remains outstanding.
5. **Database evolution — migration runner fixed 18 Sept:** `src/lib/db.ts` now runs each migration file as one multi-statement command (`pg`'s plain-text `.query()`, PGlite's `.exec()`) instead of stripping `--` comments and splitting on `;` — the old approach broke on a semicolon inside a string literal, a comment, or a function body, and required the comment-stripping workaround for the same reason. The existing transaction/advisory-lock guarantees are unchanged. Verified against a completely fresh database (all 23 migrations applying cleanly through the new runner, then a full demo-wedding flow working against it) and against the existing local dev database (idempotent skip of already-applied migrations, no re-run). Still open: measure the serialized per-process database queue before scaling.
6. **Operational evidence:** exercise restore into a disposable PostgreSQL database and private object store, webhook replay handling, provider failure/retry behavior and deployment request limits. Avoid using production-connected `.env.local` for tests that create or delete records.

## Structure and documentation

Keep `src/app` as route composition. Continue using `src/components/studio` and `src/components/guest` for workflow UI. New pure policies belong in `src/lib/security`; database-backed session and wedding authorization remain separate from those policies.

Next extraction: move admin, household RSVP, guest photos and finder operations out of the approximately 1,500-line catch-all API into focused service modules, one workflow per change. Keep authorization at every callable boundary and retain the current route contracts. Do not scatter authorization into UI components.

The root layout imports around thirty global CSS files. Establish route ownership and an import/dependency map before moving them: import order currently affects the cascade. Migrate self-contained components to CSS Modules with visual comparisons; move workflow styles into route layouts only after testing navigation and guest previews. A wholesale file move would offer little protection against regressions.

Treat this report as the current review, `DEPLOYMENT.md` as the environment contract, `OPERATIONS.md` as the runbook, and `LAUNCH-STATUS.md` as release evidence. Historical plans should be labelled with their dates. The README had stale statements about storage, migrations, retries and demo cleanup; those were corrected in this pass. Older documents still need reconciliation before serving as operational instructions.

## Post-review addendum (18 Sept, later same day)

Not from the original review — found while the client tested a mock wedding: publishing a "reminder" message had no duplicate protection, so repeatedly composing and publishing the same reminder template (e.g. from RSVPs → "Prepare a reminder") stacked near-identical notes on a guest's invitation with no warning. `src/lib/messages.ts` now blocks publishing/sending an exact audience+channel+subject match within 24 hours of a prior send, with a matching client-side warning in `src/components/studio/messages.tsx` before the couple even tries. Verified with a PGlite SQL smoke test and live against a running server (identical resend blocked, differently-worded resend still sends).

**Day-of finder (`/f/<slug>`) contrast fix:** the client flagged the live page as looking broken. Root cause: `.finder-next` (the "happening now / next event" card) had no background at all, so the page's dot-grid texture showed straight through it, and every text element inside used low opacity (0.5–0.8) — cumulatively close to illegible, unlike `.finder-result` a little further down the same page, which already had a solid card background, shadow, and printed-card outline. `src/app/day-finder.css` now gives `.finder-next` the same treatment. Also fixed while there: a real (not cosmetic) bug in `src/components/day-finder.tsx` where the couple's names rendered with no space before the separator ("Elena Moretti& Matteo Ricci"). Verified against a local demo wedding, both the pre-search and found-a-seat states, desktop and mobile.

**Ownership transfer — implemented (was unimplemented per `docs/LAUNCH-STATUS.md`):** `src/lib/ownership-transfer.ts`, migration `024_ownership_transfer.sql`. Modeled on the existing collaborator-invite pattern (offer by email, only activates once that email's own account is verified) but requires the recipient's explicit accept/decline rather than activating unilaterally, since this hands over full control rather than shared access. Only one pending offer per wedding; expires after 7 days; the worker now marks expired offers rather than leaving them inert forever. Verified with a PGlite smoke test (7 checks: single-pending constraint, case-insensitive recipient lookup, accept actually moves `owner_id`, a resolved transfer can't be replayed, expired offers don't show up) and a full live end-to-end pass covering every rejection boundary (unverified recipient, wrong account, wrong email even once verified) plus the complete accept path confirmed via the Studio API (new owner gets access, old owner loses it).
